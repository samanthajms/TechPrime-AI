1The system in one page

TechPrime AI runs one computer store branch end to end: the shelf (inventory), the counter (cashier POS), the website (online store), the office (reports and forecasts) and a few “smart” helpers.

The problem it solves

A computer parts store usually keeps stock in a spreadsheet, sells at the counter with a separate cash register, and has no online shop. Then stock counts drift, nobody knows which items are running out until they are gone, and buying decisions are guesses. TechPrime AI puts all of this in one database, so a sale at the counter, an online order and a delivery from a supplier all change the same stock number right away.

Who uses it

CashierStore counterScan barcodes and sell to walk-in customers, print receipts.
Inventory CustodianStock roomMaintain products, receive deliveries (stock-in), process online orders, watch stock alerts.
Retail OfficerOfficeSales reports, sales history, exports, forecasts.
AdminOfficeUser accounts, activity (audit) logs, security settings, overview of everything.

The three AI features

1 · Forecasting

Predicts product demand and sales revenue 1 to 3 months ahead using an XGBoost model (a separate Python service). Also suggests when to reorder and how much.

2 · Primo chatbot

A shop assistant that understands questions in English and Taglish. An SVM model guesses what the customer wants (price? stock? order status?), then real data comes from the database.

3 · Build a PC

Checks that parts fit together (CPU socket, RAM type, case size, power) using rules, then a Random Forest ranks the compatible parts and marks the top 3 as “Recommended”.

Plus: barcode POS

Not AI, but a core feature: USB scanner support, check-digit validation, VAT-inclusive receipts and sale transactions that can never oversell.

In simple words

One database is the “single source of truth”. Five kinds of users each get their own screens. Three AI helpers sit on top: one predicts the future (forecast), one talks to customers (Primo), one helps customers choose PC parts (Build a PC).

The pattern every page follows

JSON endpoints (used by JavaScript, like the POS) follow a matching rule: a business problem such as “not enough stock” comes back as HTTP 200 with {ok:false, error, message}, so the screen can show the message. Only security problems (not logged in, wrong role, bad CSRF token, wrong method) use 4xx error codes.

4Accounts, login and security

Customers register themselves and activate by e-mail. Staff accounts are created by the Admin. Everyone signs in on the same login page and is sent to their own area.

Customer registration and activation

  1. Fill in the form (register.php): name, surname, age, phone, full Philippine address (province → city → barangay pickers), e-mail and password. The e-mail and phone are checked live for duplicates.
  2. Password rules come from the Admin’s Settings page (default: at least 8 characters with uppercase, lowercase, a number and a special character).
  3. Saved safely: the password is hashed with bcrypt (password_hash). The real password is never stored. The account starts as is_verified = 0.
  4. Activation e-mail: a random 64-character token plus an expiry time (24 hours) is saved and e-mailed as a link. Clicking it (activitate.php) sets is_verified = 1 and deletes the token so the link works only once.
  5. Expired link? Logging in with the right password opens a “Resend activation link” screen (with a wait time between resends).

6Online store and the order lifecycle

An online order moves through fixed stages, like a package tracker. Each stage has a clear owner, and stock is deducted only once, at the very end.

Shopping before the order

  • Browsing: Home, Shop (with categories, brands, price filters and live search), product detail pages, recently viewed items, wishlist.
  • Cart: guests have a cart in their session. On login, ep_sync_cart_on_login() merges it into the saved database cart (keeping the higher quantity if the item is in both), so a cart survives logout and login.
  • Checkout: choose a saved address, a new address, or Pick up at the store, and give a phone number. Delivery orders are handed to Lalamove.
  • Double-submit protection: a one-time checkout token means clicking “Place order” twice creates only one order.

The order stages

Place orderCustomerep_place_unpaid_order()Locks each product row and checks stock is enough; creates the orders row (status to_pay, unpaid) and order_items; removes the items from the cart; notifies the customer and the custodian. Stock is not deducted yet.
PayCustomerep_mark_order_paid()Sets payment_status = 'paid', a unique payment reference and paid_at. Pickup orders jump to to_receive. The custodian is told “ready to Accept”.
AcceptCustodianep_accept_order()Only if paid and no cancellation pending → to_ship; creates a shipments row (carrier Lalamove for delivery).

In simple words · why deduct stock only at “Completed”?

An order can still be cancelled before it is paid, so taking stock away at order time would make items look sold out when they are not. The stock is checked (and locked) when the order is placed, and actually removed when the customer has the item. The stock_deducted flag makes sure it happens only once, even if the button is clicked twice.

Example · one order from start to end (illustrative)
  1. Ana orders 1 × 16 GB RAM kit (stock 9). The order becomes #ORD-120, To Pay. Stock is still 9.
  2. Ana pays. The custodian’s bell shows “Paid order #ORD-120 ready to Accept”.
  3. The custodian clicks Accept → To Ship, packs it, and sets it to To Receive when Lalamove picks it up.
  4. Ana clicks Item Received → stock 9 → 8, order Completed. The sale now appears in the Retail Officer’s reports.
  5. No new stock alert: 9 and 8 are both in the “low” level (6–15), and alerts fire only when the level changes. Had the stock gone from 16 to 15, every stock-alert user would get “low in stock (15 left)”.
Be honest about · online payment

The Pay page is a placeholder for the school project (the page itself says so). Clicking “Pay Now” marks the order paid with a generated reference. No real money moves and no payment gateway is called. A real gateway such as PayMongo would replace only this one step; the rest of the order flow stays the same.

7Cashier point of sale (POS)

The counter screen for walk-in customers: scan, review the cart, take payment, print the receipt. The important part is what happens behind “Complete sale”.

The flow at the counter

  1. Scan. A USB barcode scanner works like a very fast keyboard: it “types” the digits and presses Enter. barcode_scanner.js spots this (keys arriving a few milliseconds apart), so scanning works without clicking into a field first.
  2. Validate the check digit in the browser and again on the server (see the example below). A misread code is rejected right away.
  3. Look up the product (backend/api/barcode_lookup.php): name, price and stock come back and the item is added to the cart.
  4. Choose payment: Cash (enter the amount tendered, change is computed), GCash, Maya or Card (a reference number is required).
  5. Complete sale (backend/api/stock_out.php → pos_complete_sale()): one database transaction does everything, or nothing.
  6. Receipt opens with the invoice number (format INV-YYYYMMDD-000123), VAT breakdown and change, and prints in the same tab.

Barcode check digit, worked example

Every UPC/EAN barcode ends with a check digit computed from the other digits. If one digit is misread, the check digit no longer matches. The system accepts UPC-A (12 digits), UPC-E (8), EAN-13 (13) and EAN-8 (8).

Example · is 4800123456786 a valid EAN-13?
Digit480012345678check
Weight131313131313–
Product42400163125187246

Sum = 104. Check digit = (10 − (104 mod 10)) mod 10 = (10 − 4) mod 10 = 6. The last digit is 6, so the code is valid. If the scanner misread one digit, for example 4800123456796, the sum becomes 107, the expected check digit becomes 3 instead of 6, and the code is rejected with “Invalid barcode check digit”.

The code stores every barcode in one normalized form (12-digit UPC-A gets a leading 0 to become 13 digits; UPC-E is expanded first), so the same product is found whichever format is scanned. Products without a barcode can get an in-store one: 21 + the 10-digit product ID + a check digit (product #57 → 2100000000579), printable as a label.

What “Complete sale” does inside the database

Why lock the rows? (overselling)

Two cashiers sell the last mouse at the same second. Without a lock, both read “stock 1” and both sell. With FOR UPDATE, the second cashier waits until the first finishes, then reads “stock 0” and gets “Not enough stock”. The database rule CHECK (stock >= 0) is a last safety net.

Why lock in ID order? (deadlock)

If sale A locks mouse then keyboard while sale B locks keyboard then mouse, each waits for the other forever. Locking always in the same order (lowest ID first) makes that impossible.

What is client_ref? (idempotency)

The POS screen creates a random ID (UUID) for each sale before sending it. If the Wi-Fi drops and the cashier clicks again, the server sees the same ID and returns the first sale instead of charging twice. The column is UNIQUE, so even two requests at the same instant cannot both succeed.

Why integer centavos?

Computers store decimals like 0.1 inaccurately. ₱1,234.50 is handled as 123450 centavos, so totals and change are always exact.

Example · VAT on a receipt (illustrative)

Prices already include 12% VAT. The cart total is ₱3,450.00 (345,000 centavos).

  • VATable sales = 345,000 ÷ 1.12 = 308,035.7 → rounded to ₱3,080.36
  • VAT = total − VATable = 345,000 − 308,036 = ₱369.64
  • Customer pays ₱4,000.00 cash → change = ₱550.00

VAT is total minus VATable (not a separate rounding), so the two always add up to the total exactly.

Other cashier screens

  • Dashboard: today’s sales count and total for this cashier, recent sales, a live stock-alert panel (refreshes every 30 seconds).
  • Stock Alerts: out / critical / low products, read only, so the cashier can tell customers what is running out.
  • Limits: at most 999 per line and 200 different products per sale; references are letters, digits, spaces and - / #, up to 64 characters.

8Inventory custodian

The custodian owns the product list and the stock numbers, receives supplier deliveries and moves online orders forward.

Products (Stocks page)

  • Add, edit, delete (single or bulk) products: name, category, price, stock, description, image, SKU (EasyPC’s internal item code) and barcode.
  • The catalog was imported from EasyPC’s item list (Oasis-Itemlist.csv, 261 products) with images per category.
  • Print a barcode label, or generate an in-store barcode for products that have none.

Stock-in (receiving a delivery)

  1. Scan the product’s barcode (same scanner logic as the POS).
  2. Enter the quantity (1 to 10,000), choose the supplier (required) and an optional reference number (for example the delivery receipt number).
  3. pos_stock_in() locks the product row, adds the quantity, writes a stock_movements row of type stock_in (with stock before and after, supplier, reference) and an audit log line like stock 3 → 23 (+20), supplier: Kingston.
  4. If the product was out or low and is now fine, the alert roles get “stock increased by 20 (now 23)”.
Be honest about · suppliers

There is no separate suppliers table. A supplier is the product’s brand: the first word of the product name, matched against the list of shop brands (for example “Kingston FURY 16GB…” → Kingston). It keeps receiving simple, but a distributor that sells several brands can’t be recorded as itself.

Stock alert levels

Alerts fire on a change of level, not on every sale. inv_notify_stock_change(old, new) runs after every stock change (POS sale, online order completion, stock-in) and sends a bell notification to every Admin, Retail Officer and Custodian only when the stock crosses into Low, Critical or Out, or recovers. The same alert is not repeated to the same person within 24 hours.

Example · crossing levels

Stock 16 → 15: “low in stock (15 left)”. 15 → 14: nothing new. 6 → 5 after a sale: Low to Critical, both “running low”, so nothing new is sent (the Stock Alerts page still shows it as Critical). 1 → 0: “out of stock”. Then a stock-in of 20 (0 → 20): “stock increased by 20 (now 20)”.

Orders, reviews and activity

  • Orders: tabs by stage, Accept (single or bulk), status dropdown that only moves forward, cancellation requests to approve. Completed and cancelled orders are locked.
  • Reviews: all customer reviews with stars, photos and tags; the custodian can reply.
  • Activity: the custodian’s own audit trail (stock-ins, product edits, order updates, stock-outs), showing stock changes as “before → after”.
  • Forecast: the same forecast pages as Admin and Retail, including the reorder suggestions (chapter 10).

9Retail officer and admin

The office roles mostly read data: the Retail Officer turns sales into reports, the Admin manages people and settings and watches the audit trail.

What counts as a “sale” in reports

In simple words

Sales = completed online orders (status Completed) + POS sales at the counter. Orders that are unpaid, in transit or cancelled do not count. Reports are read live from the database, so a sale shows up the moment it is completed.

Retail Officer

  • Dashboard: total sales, transactions, units sold and average transaction for a chosen period (presets like Today, This week, This month, or a custom range), sales by category, a daily trend chart, a 12-month breakdown and the forecast cards.
  • Comparisons: each figure is compared with the previous period (month-over-month) and the same period a year ago (year-over-year), shown as a green ▲ or red ▼ badge.
  • Sales History: every sale line, searchable and filterable by category and customer.
  • Exports: CSV, Excel (.xlsx) or PDF, with a “prepared by” line. Each export is written to the audit log.
Example · the % change badge (illustrative)

This month ₱120,000, last month ₱100,000 → (120,000 − 100,000) ÷ 100,000 × 100 = ▲ 20.0%. If last month was ₱0, the badge says “new” instead of dividing by zero.

Admin

  • Manage Users: counts per role, locked and unverified accounts; create staff accounts (retail officer, inventory custodian, cashier), which are verified immediately; block / unblock (unblocking clears the lockout) and delete accounts.
  • Activity Logs: the full audit trail from the logs table, such as logins, lockouts, sales, stock-ins, order actions, exports, settings changes, with the user, time and IP address.
  • Settings: password policy (minimum length 6–32, upper, lower, number, special). New passwords must follow it.
  • Stock Alerts, Forecast, Messages: same shared pages as the other office roles.
Be honest about · “max failed attempts” setting

The Settings page saves a “max failed attempts” value (1–10), but login.php currently locks after a fixed 3 attempts. If asked: the lockout works at 3; connecting the setting to the login check is a small, known follow-up.

10AI #1 · Sales and demand forecasting

Looks at past monthly sales and predicts the next 1 to 3 months: how many units of each product will sell (demand) and how much money the store will make (revenue).

How a forecast reaches the screen

What XGBoost is, in plain words

In simple words

XGBoost builds many small decision trees one after another. The first tree makes a rough guess of next month’s sales; the second tree learns the mistakes of the first; the third fixes what is still wrong, and so on. Added together, hundreds of small corrections give a strong prediction. It learns from patterns such as recent months’ sales, trend and season, per product and category.

What the forecast pages show

ViewColumns / content
Product DemandUnits sold in the chosen date range, forecast units, a likely range (low–high), forecast revenue, trend (month-over-month growth), confidence and model reliability. Filter by category.
Inventory actionsCurrent stock, days of inventory left, safety stock, reorder point, stockout risk and a recommended order quantity, with an action such as “order now” or “reorder”. Shown once the service has a stock snapshot; otherwise a note explains why the columns are hidden.
SalesStore-wide revenue: actual months next to forecast months, with a confidence band (low–high).
Example · reorder point and safety stock (textbook definitions, illustrative numbers)

A product is forecast to sell 60 units next month ≈ 2 per day. The supplier takes 7 days to deliver. Keep an extra 6 units of safety stock for surprises.

  • Reorder point = daily demand × lead time + safety stock = 2 × 7 + 6 = 20. When stock falls to 20, order more.
  • Days of inventory = stock ÷ daily demand. With 30 in stock: 30 ÷ 2 = 15 days left.

These are the standard formulas the columns are named after. The exact calculation runs inside the forecast service, which lives in its own repository, not in this codebase.

If the panel asks: “Why is the first forecast slow sometimes?”

The forecast service runs on Render’s free tier, which sleeps when idle and needs up to about 50 seconds to wake. The proxy waits up to 75 seconds, and the page tells the user to retry in a minute if it’s still waking up.

11AI #2 · Primo chatbot

Primo answers shopper questions like “magkano yung ryzen 7?” or “is the RTX 4060 in stock?”. A machine-learning model decides what kind of question it is; the answer always comes from the live database.

The pipeline

The intent model: TF-IDF + SVM

An intent is the goal behind a message. Primo knows 16: greeting, goodbye, gratitude, help, product_search, product_category, product_price, stock_inquiry, product_recommendation, brand_advice, compatibility_question, saved_build, order_status, return_refund, store_information, and fallback (not understood).

  1. Clean the text: lowercase, normalize spelling.
  2. TF-IDF turns the sentence into numbers. It counts words and word pairs (“in stock”), plus 3–5-letter chunks (“mag”, “agka”, “kano”), and gives more weight to words that are rare across all examples. The letter chunks are why typos and Taglish still work.
  3. SVM (Support Vector Machine, RBF kernel) has learned boundaries that separate the 16 intents in that number space, and outputs a probability for each.
  4. Threshold: if the top probability is below 0.32, the answer is “fallback” (ask to rephrase) instead of a risky guess.

Why the LLM can’t make things up

In simple words

The LLM (Groq, model gpt-oss-20b) is only allowed to rephrase a sentence that PHP already built from the database. After it answers, primo_phrase_keeps_facts() checks that every peso amount is the same, no new peso amount appeared, the product name is still there and every “N on hand” is unchanged. If anything differs, the original database sentence is used. If Groq is off, Primo still works with the plain sentences.

Privacy and abuse protection

  • E-mail addresses and phone numbers are masked before anything goes to the LLM or into the “unanswered questions” log.
  • The unanswered log keeps only the masked message text (no user ID, session or IP), at most 30 per visitor, deleted after 90 days. Staff review it and add good examples to the training data: the model learns from real questions.
  • Rate limits: 15 messages per minute per browser, 60 per IP address.
Be honest about

“help” and “fallback” are the weakest intents (about 4–6 out of 10 on the hard set), and the test sentences were written by the same team as the training data, so they aren’t fully independent. Real shopper messages from the unanswered log are the planned next source of data.

12AI #3 · Build a PC recommender

The customer picks a purpose (School, Office, Gaming, Content Creation, or Not sure yet), an optional budget, and then a part for each slot. Two layers help: rules remove parts that won’t fit, then a Random Forest ranks the parts that remain.

Layer 1 · Compatibility rules (includes/pc_compatibility.php)

Each product’s name and description are read for tags such as socket (AM4, AM5, LGA1700), memory type (DDR4/DDR5), form factor (ITX, mATX, ATX, E-ATX), storage type (NVMe/SATA) and wattage. Then:

RuleMessage the customer sees
CPU socket = motherboard socket“CPU socket mismatch”
RAM type = motherboard type (and what the CPU supports)“RAM type mismatch” / “this processor needs DDR5”
Cooler socket fits the CPU/motherboard“cooler socket mismatch”
Case size ≥ motherboard size (ITX < mATX < ATX < E-ATX)“case form factor too small”
PSU watts ≥ estimated draw (CPU 65 W + board 40 W + GPU 180 W + RAM 10 W + storage 15 W)“PSU wattage too low for estimated power draw”

An extra check refuses any part that would leave another required part with no compatible option in stock (a “dead end”).

Layer 2 · The Random Forest

In simple words

A decision tree is a flowchart of yes/no questions (“Is this part much pricier than the rest of the build?”, “Does the purpose need a graphics card?”). A Random Forest is 60 such trees, each trained on a slightly different random sample. Each tree votes how good a fit the part is; the forest averages the votes. Many imperfect voters together are more reliable than one.

Example · scoring one graphics card for a Gaming build (illustrative)

Tree 1 says 0.9, tree 2 says 0.7, tree 3 says 0.8 … the average of all 60 is 0.78. That is above the threshold 0.5, so it is a “good fit”. Among all compatible GPUs, the three highest averages get the Recommended badge with a reason (“Fits the parts you already picked”). A part that fits the rules but scores low gets a note such as “Pricier than the rest of this build needs.”

What the trees look at (23 features): the purpose, which slot, how the part’s price tier compares with the rest of the build, overall build level, GPU level, performance tier, balance, cooling margin, dual-channel memory, PSU headroom and rating, ATX 3.0, case bundle, form-factor slack, brand match, built-in graphics, bundled cooler, VRAM and budget slack. The most important ones are budget slack (19%), slot (14%), price-tier gap (13%) and performance tier (11%).

Where the training data comes from

  • Rule rows (53,985): random partial builds from the real catalog, for every purpose and several sample budgets (₱30k to ₱200k). Each candidate part is labelled good/not good by expert rules.
  • Real rows (739): real customer choices from saved builds, online orders and POS sales. One part is hidden; the part the customer actually chose is “good”. Real picks count 5× more, so the model follows customers where they disagree with the rules.

How well it works (from models/forest.json)

TestResultMeaning
Accuracy, 4-fold cross-validation grouped by build99.0%Agrees with the labels on builds it never saw (F1 0.989).
Hit@3 on real customer builds65.1%Hide a part a real customer chose: in 65% of cases it is in the model’s top 3.
Same test, expert rules alone57.0%The model beats every simpler method, which shows the machine learning adds value over plain rules.
Same test, closest price range51.2%
Same test, random picks39.9%
Be honest about

The 99% is high partly because most rows are labelled by rules, which a forest learns easily. On the 739 real rows alone accuracy is about 47%, because a customer’s single choice is “right” and every other good part counts as “wrong”. That’s why Hit@3 (is the real choice in the top 3?) is the fairer measure. Compatibility also depends on product names and descriptions being written clearly.

Nightly self-improvement (ml/pc_recommend/retrain.py)

“Build it for me” uses the same pieces: given a purpose and budget, it fills each empty slot in order (CPU, motherboard, memory, GPU if the purpose needs one, storage, PSU, case, cooler, fans), using a budget share per slot for that purpose and the best-scoring compatible part. Builds can be saved to the account and added to the cart.

  • Time: timestamps are saved in UTC and shown in Philippine time (Asia/Manila), so reports are correct regardless of the server’s location.

15Defense prep: likely questions

Short, honest answers. Say what the system does, how you know it works, and what you would improve.

What makes the system “AI”?
Three trained models: an XGBoost model forecasts demand and revenue; an SVM classifies the intent of chatbot messages; a Random Forest ranks compatible PC parts. Each was evaluated: Primo 83.8% on a held-out hard test set, the forest 99.0% cross-validated accuracy and 65% Hit@3 on real builds, better than rules alone (57%).
How do you prevent selling an item that is already out of stock?
At the POS, the sale locks the product rows (FOR UPDATE), re-checks stock inside the transaction, deducts with WHERE stock >= qty, and the database itself forbids negative stock. If any check fails, the whole sale rolls back. Online orders check and lock stock when placed and deduct once at completion.
What if the cashier clicks “Complete sale” twice or the network drops?
Each sale carries a unique client_ref created by the POS screen. A repeated request returns the same sale instead of a new one; the UNIQUE constraint covers even simultaneous requests.
Why is the stock of an online order not deducted when the order is placed?
The order can still be cancelled while unpaid. Stock is validated at placement and deducted exactly once, when the customer confirms receipt (or staff completes it), guarded by the stock_deducted flag.
How are passwords protected?
bcrypt hashes, an admin-configurable complexity policy, lockout after 3 wrong attempts, identical error messages for wrong e-mail or password, a new session ID at login and a 15-minute idle timeout.
How do you stop one role from opening another role’s pages?
Every page starts with checkSessionTimeout() and checkRole(); JSON endpoints check the session role and return 403. Typing another role’s URL redirects to login.
Can the chatbot give a wrong price?
Prices and stock always come from the database. The LLM only rephrases, and the reply is thrown away if any price, product name or quantity changed. If the model is unsure (below 0.32 confidence) Primo asks the customer to rephrase instead of guessing.
How does Primo understand Taglish and typos?
TF-IDF uses 3–5 character chunks as well as words, so “magkano”, “mgkano” and “magkanoo” share most chunks. The training data includes 102 Taglish/Filipino examples.
How does the forecast help the business?
It shows which products will sell in the next 1–3 months and turns that into inventory actions: reorder point, safety stock, days of inventory left and a recommended order quantity, so buying decisions are based on data.
How does the Build-a-PC know two parts are compatible?
It reads the socket, memory type, form factor, storage type and wattage from product names and descriptions, then applies fixed rules (socket match, DDR match, case ≥ board size, PSU ≥ estimated draw). Only parts that pass are ranked by the model.
Does the model keep learning?
Yes. The Build-a-PC forest retrains every night from new saved builds and sales, and goes live only if it passes the data-size and accuracy checks. Primo’s unanswered questions are reviewed and added to its training data.
How is every action traceable?
logActivity() records the user, action, details (for stock: before → after) and IP for logins, sales, stock-ins, order actions, exports and settings changes. Admin sees all of it in Activity Logs.
What happens if the database or an AI service is down?
Database down: a branded “can’t connect” page, details only in the server log. Primo down: “temporarily unavailable” message. Groq down: Primo still answers with plain database sentences. Forecast asleep: a “waking up, retry” message. Build a PC without the model file: the rules still filter parts.

16Glossary

Terms you may hear or use during the defense.

Audit trail / logA record of who did what and when (logs table).
bcrypt / hashA one-way scramble of a password. You can check a password against it, but you can’t reverse it.
Check digitThe last digit of a barcode, computed from the others to catch misreads.
Confidence thresholdThe minimum probability before Primo trusts its guess (0.32).
Cross-validationTesting a model on parts of the data it didn’t train on, several times, and averaging.
CSRF tokenA secret value in each form so other websites can’t submit forms as the user.
DeadlockTwo processes each waiting for a lock the other holds. Avoided by locking in a fixed order.
F1 scoreOne number that balances precision (how many “yes” answers were right) and recall (how many real “yes” cases were found).
Hit@3How often the correct answer is among the top 3 suggestions.
IdempotentDoing the same request twice has the same effect as doing it once.
IntentThe purpose behind a chat message (price, stock, order status…).
LLMLarge Language Model, a text-generating AI (used here only to rephrase).
PDO / prepared statementPHP’s database layer; user input is sent separately from the SQL so it can’t be run as code.
Random ForestMany decision trees that vote; the average vote is the prediction.
Reorder pointThe stock level at which you should order more (daily demand × lead time + safety stock).
Row lock (FOR UPDATE)Reserves a database row so no one else can change it until the transaction ends.
Safety stockExtra units kept for unexpected demand or late deliveries.
SessionThe server’s memory of a logged-in user, linked to a browser cookie.
SKUStock Keeping Unit, the store’s own product code.
SVMSupport Vector Machine, a model that learns boundaries between categories.
TF-IDFTurns text into numbers; rare, distinctive words weigh more than common ones.
Transaction / rollbackA group of database changes that are saved together, or all undone if one fails.
UPC / EANStandard product barcode formats (12 / 13 / 8 digits).
UUIDA random, practically unique ID (used as the POS client_ref).
VAT-inclusiveThe shelf price already contains the 12% VAT; VAT = total − total ÷ 1.12.
XGBoostGradient-boosted trees: each new tree corrects the errors of the previous ones.
